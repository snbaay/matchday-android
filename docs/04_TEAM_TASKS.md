# 04 — Персональные задания и разделение ownership

> Пути ниже относятся к исходным заданиям Week 12. После согласованного общего рефакторинга владельцы сохраняют свои области в `presentation/ui/**`; архитектура и новые пути описаны в `09_CLEAN_ARCHITECTURE.md`.

**Важно о коммитах:** ниже **40 проверяемых рабочих этапов**, а не указание делать 40 пустых коммитов. Каждый этап должен оставлять полезное изменение: новый работающий компонент, поведение, тест или существенную документацию. Этапы могут занимать более одного коммита; не дробите бессмысленно ради счётчика. Для оценки требуются **≥10 осмысленных индивидуальных коммитов от каждого**. Чужие коммиты и коммиты бота нельзя представлять как свои.

Перед работой участник открывает своё задание и шаблон своей роли в `prompts/ROLE_PROMPTS.md`. После изменений он проверяет дифф и описывает сделанное в 1–3 предложениях.

## Строгий порядок зависимостей

```text
P1-01..P1-09 -> foundation PR approved -> merge into main
                                     |
                                     +-- P2-01..P2-10 -> own PR(s)
                                     +-- P3-01..P3-10 -> own PR(s)
                                     +-- P4-01..P4-10 -> own PR(s)
                                                     |
                                       P1-10: integration PR -> QA -> defense
```

Работы P2/P3/P4 можно выполнять параллельно **после того**, как P1 опубликует модели и контракты в `main`. Несогласованность контракта фиксируется в Issue и решается **до** изменения модели.

## Владельцы кода и проверки

- P1 ревьюит PR P2/P3/P4; P2 ревьюит интеграционные PR P1.
- P3 и P4 могут друг друга проверять на работоспособность UI; финальный merge решает человек-ревьюер.
- Каждый PR содержит описание изменений, скриншот для изменений интерфейса, результаты тестов и объяснение работы.
