# 05 — Работа с Git и GitHub

## A. Подготовка у каждого участника (один раз)

1. Установить стабильную версию Android Studio и Git for Windows. Для работы с Git использовать GitHub Desktop или терминал.
2. Создать собственный GitHub-аккаунт. Все четыре человека используют **отдельные** учётные записи, а не общий пароль.
3. Подключить Git к **своему** аккаунту GitHub. Настроить имя/email на своём компьютере:

   ```powershell
   git config --global user.name "Your Own Name"
   git config --global user.email "your-verified-github-email@example.com"
   git config --global --get user.name
   git config --global --get user.email
   ```

   Если хотите скрыть email, используйте GitHub `noreply`-адрес из настроек GitHub, а не выдуманный.
4. Каждый участник открывает проект в Android Studio и проверяет запуск на эмуляторе или устройстве.

## B. Создание репозитория: только P1

**Рекомендуемый путь:** сначала Android Studio → `New Project` → `Empty Activity` → Kotlin, Compose, имя `Matchday`, пакет `com.example.matchday`, minSdk 26. Сделать Gradle Sync и запустить базовый экран.

Затем на github.com → New Repository:

- Имя: `matchday-android`.
- Public или Private по правилам курса. **Public** позволяет защитить ветку на GitHub Free; для Private на бесплатном GitHub защита ветки может быть недоступна (проверьте настройки аккаунта). Если Private — добавить преподавателя с доступом, иначе одной ссылки недостаточно.
- При создании GitHub repo **не** создавать вторые README/`.gitignore`/license, если локальный проект уже содержит файлы: это исключает разные первые истории.
- Settings → Collaborators → Add people → пригласить троих по GitHub username; каждый должен принять приглашение.

Команды из PowerShell в **корне Android-проекта**:

```powershell
git init
git branch -M main
git status
# Сначала убедиться, что .gitignore не даёт добавить local.properties, .gradle/, build/, ключи
# Скопировать документацию в корень проекта, заполнить имена в README
git add .
git diff --cached --stat
git commit -m "chore: initialize runnable Matchday Android project and docs"
git remote add origin https://github.com/OWNER/matchday-android.git
git push -u origin main
```

`OWNER` заменить **реальным** username владельца. Если Git уже включён Android Studio, `git init` безопасно обнаружит существующий репозиторий, но не удаляйте старые ветки. Никогда не вводите пароль GitHub в чат с агентом и не коммитьте токены.

## C. Защита main (если доступна в вашем плане)

GitHub → Repository → Settings → Branches → Add branch protection rule (или Settings → Rules → Rulesets), target `main`:

- Require a pull request before merging.
- Require at least **1 approving review** другого участника.
- Block force pushes and branch deletion.
- По возможности включить status checks после настройки работающего CI (не включать несуществующую проверку: она заблокирует PR).
- Не разрешать обходить правила автоматически, если есть такой переключатель.

**Ограничение тарифов GitHub:** стандартная защита веток с GitHub Free доступна для публичных репозиториев; на приватных — в зависимости от тарифа. Если в Private Free настройки недоступны, команда вручную придерживается того же правила: изменения только через PR и review.

## D. Как все клонируют и работают (Windows)

После принятия приглашения каждый участник клонирует репозиторий **на свой компьютер**:

```powershell
git clone https://github.com/OWNER/matchday-android.git
cd matchday-android
git status
```

Для каждой новой задачи создавайте **свежую ветку от обновлённого main**:

```powershell
git switch main
git pull --ff-only origin main
git switch -c feat/p3-team-dialog
# Работа в своей зоне, локальные проверки
git status
git diff
git add app/src/main/java/com/example/matchday/ui/teams
# Указывать конкретные файлы для изменений, не слепо git add .
git commit -m "feat(teams): add create-team dialog with validation"
git push -u origin feat/p3-team-dialog
```

Команда выше — **пример P3**; у других роли и пути отличаются. Для следующей задачи — новая ветка `feat/pX-short-task` от актуального `main`. Никогда не создавайте одноимённые ветки одновременно на разных компьютерах и не работайте четырьмя агентами в одном working directory.

## E. Pull Request и merge

1. GitHub предлагает `Compare & pull request` после push. Base branch `main`, compare — своя feature branch.
2. Автор заполняет `.github/pull_request_template.md`: проблема, файлы, тесты, скриншот, как проверить.
3. Другой участник проверяет дифф. P1 проверяет PR участников P2, P3 и P4. P2 проверяет PR участника P1.
4. Ревьюер отмечает в PR замечания и проверки, которые нужно повторить.
5. После замечаний автор делает новые корректирующие коммиты в **своей** ветке и пушит.
6. Человек-ревьюер выполняет **Merge pull request** после проверок. Не включать auto-merge и не делать `Squash and merge`, если нужно сохранить историю отдельных осмысленных коммитов каждого (squash может скрыть их как индивидуальные коммиты `main`).
7. После merge каждый выполняет:

   ```powershell
   git switch main
   git pull --ff-only origin main
   ```

8. Удаление feature branch после merge — необязательно и выполняется только автором/lead; никогда не удаляйте `main`.

## F. Работа над задачей

Откройте проект в рабочей копии и проверьте, что доступны файлы проекта и Git Diff.

1. Открыть корень **локального** репозитория, а не одну случайную `.kt`-папку.
2. Прочитать `CONTRIBUTING.md` и документы из `docs/`, относящиеся к задаче.
3. Указать роль, ID этапа и разрешённые папки по шаблону в `prompts/ROLE_PROMPTS.md`.
4. Перед изменениями записать план и список файлов. Правки вне своей зоны согласовать с P1.
5. Для работы, затрагивающей Gradle, navigation или repository, использовать **только P1**; остальные сообщают об ошибках в Issue, не чинят их самостоятельно.
6. Вносить изменения и запускать проверки в своей рабочей ветке. Отправлять коммиты в эту ветку и открывать PR после проверок. Ревьюер отвечает за объединение с `main`.
7. Ревьюер проверяет дифф и сборку в Android Studio. Автор исправляет замечания до одобрения PR.

Если Android SDK недоступен, укажите в PR, что `assembleDebug` ещё предстоит выполнить, и проверьте сборку локально.

### Учёт 10 коммитов и авторства

- Проверяйте фактическое авторство коммитов и указывайте вклад каждого участника.
- Коммиты должны содержать реальное развитие проекта. `fix: whitespace`, пустой коммит, переключение одной строки туда-обратно и случайное переименование ради числа не подходят.
- Участник отвечает за понимание и проверку кода. Соблюдайте правила курса по раскрытию использованных инструментов и сообщайте преподавателю фактическую информацию.
- Для проверки выполнить на `main`:

  ```powershell
  git log --pretty=format:"%h %an <%ae> %s" --no-merges
  git shortlog -sne --no-merges HEAD
  ```

  В истории GitHub проверьте оба поля, Author и Committer.

## G. Если сломалось или возник конфликт

**1. Задача затрагивает файл другого участника.** Открыть Issue с описанием причины. Владелец файла оформляет отдельный PR, после чего автор продолжает работу.

**2. Merge conflict.** Владелец ветки обновляет её от `main`, разрешает конфликт только вместе с затронутым владельцем, ещё раз запускает сборку и тесты. Никогда не нажимать «Accept all incoming» не читая код.

**3. Android Studio не собирает.** Сначала Gradle Sync, ошибки зависимости/импорта, компилятор. Отправить P1 точный лог + ветку и sha. Не менять версии библиотек наугад.

**4. После merge перестал работать экран.** Остановить новые merge, исправить минимальным новым PR; не переписывать историю `main`.

**5. PR всё ещё не проверен.** Он не считается готовым для защиты. Если понадобится, урезать фичу, а не объединять непроверенный код.
